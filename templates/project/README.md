# OpenSpec Project Bootstrap

Ask the agent in the project session to apply this directory to the root of a
participating project. The agent must inspect existing files, merge safely, run
the preflight, interview the user, and maintain project artifacts. The user
must not be asked to edit template files manually.

## Contents

- `PRODUCT.md` captures stable product facts and constraints.
- `DESIGN.md` is optional and records enduring system-level decisions.
- `PACKAGE.md` configures project-specific packaging, clean-smoke, content-check,
  release, and rollback evidence.
- `openspec/` is the unmodified OpenSpec `spec-driven` configuration.
- `.opencode/commands/` contains the five reviewed SDD adaptations of the
  OpenSpec `core` command surface generated by `@fission-ai/openspec@1.5.0`.

## Prerequisites

The project command bodies invoke `openspec` directly. Before invoking an
`/opsx-*` command, install the reviewed CLI on `PATH` and confirm its version:

```powershell
npm install --global @fission-ai/openspec@1.5.0
openspec --version
```

`npx --yes @fission-ai/openspec@1.5.0` is suitable for an explicit one-off CLI
operation, but it does not make the bare `openspec` command available to the
project command bodies. Restart or reload OpenCode after copying the bootstrap
so it discovers the `.opencode/commands/opsx-*.md` files.

Run the preflight from the copied project before using an `/opsx-*` command:

```powershell
PowerShell -ExecutionPolicy Bypass -File .\Test-OpenSpecBootstrapPreflight.ps1
```

It fails when the required CLI is absent or version-mismatched. It reports
unsupported command and skill dependencies from the project command sources
as actionable warnings; these are OpenSpec `core` profile limitations, not
custom commands added by this bootstrap.

For an existing participating project, ask the agent to diff and update only
the five `.opencode/commands/opsx-*.md` files and the copied preflight from this
template. It must preserve `PRODUCT.md`, `DESIGN.md`, `PACKAGE.md`, active
changes, and all project facts, then rerun the preflight and request an OpenCode
reload. The user must not perform the file merge manually.

## Start A Change

Use the project commands in OpenCode. Every command interviews for missing
material facts adaptively, without a fixed question or option count. It edits
artifacts itself and ends with the next command plus an OpenChamber
Focus/Goal/worktree/MultiRun recommendation.

Use `/opsx-explore <idea>` for product onboarding or brainstorming. It updates
`PRODUCT.md`, `DESIGN.md`, and surface briefs only after user confirmation and
does not implement application code. Use `/opsx-propose <change-name>` to create
a change and all apply-required artifacts. The OpenSpec CLI's `instructions`
output is authoritative for each artifact's current structure.
The framework's `templates/openspec/` references are not copied with this
bootstrap; use them from the framework checkout only as concise guidance.

For a new project that does not copy this bootstrap, generate the same core
integration with:

```powershell
npx --yes @fission-ai/openspec@1.5.0 init --tools opencode --profile core
```

## Validate

From the participating project root, validate the active change before marking
it verified or archiving it:

```powershell
npx --yes @fission-ai/openspec@1.5.0 validate <change-name> --strict --no-interactive
```

## Core Profile Limitation

The `core` profile generates no custom continuation command for a blocked
change. The bootstrap must not introduce one. The adapted `/opsx-apply` command
therefore completes missing artifacts automatically through the installed CLI:

1. Run `openspec status --change <name> --json` and read the `artifacts`
   list. Each `not_done` entry has a stable `id`; do not assume the default
   `proposal`, `specs`, `design`, or `tasks` filenames.
2. For each missing artifact, run
   `openspec instructions <artifact-id> --change <name> --json`. The CLI
   returns the schema-specific frontmatter, required sections, and any
   `contextFiles` paths to populate.
3. Read every `contextFiles` path returned by the instructions.
4. Create or update the artifact at the resolved path so it matches the
   CLI's required structure, then re-run `openspec status --change <name> --json`.
   Repeat until no listed artifact is `not_done`.
5. Re-run `openspec instructions apply --change <name> --json`. The
   `state` should now be `ready` or `in_progress` rather than `blocked`.

This is a documented upstream `core` profile limitation, not a custom
command added by this bootstrap.

On Windows PowerShell, the adapted `/opsx-archive` command uses the portable
installed CLI directly and never creates archive directories manually:

```powershell
openspec archive <change-name>
```

## Release, Approval, And Pre-Release Validation

Before archive, the adapted `/opsx-archive` prompt takes `changeRoot` from the
status JSON and uses `<changeRoot>/release.md` and
`<changeRoot>/verification.md`. It refuses to archive without a successful
recorded release, exact approval, complete requirement coverage, successful
post-release smoke, and fresh strict validation. The bootstrap does not add an
additional archive command; it relies on the installed CLI and the adapted
prompt's gate so an unapproved release cannot archive.

## Package And Release

Before packaging, the agent inspects project tooling, interviews the user only
for unresolved material release facts, and updates `PACKAGE.md` itself. It then
runs the selected build/package command, verifies the artifact in a new
temporary environment, records its SHA-256 checksum, and writes evidence to
`<changeRoot>/verification.md` and `<changeRoot>/release.md`.

Packaging is not a release authorization. Before any publish, deploy, tag,
push, merge, or other external write, obtain and record explicit user approval
for the exact version, release notes, target/environment, known warnings,
rollback plan, and external action. After the approved action and post-release
smoke succeed, run strict validation and `openspec archive <change-name>`.
Do not archive a failed, cancelled, or unapproved release.

A Goal may prepare package and release evidence only to `ready for release`.
It must stop before the external action and archive; both remain outside the
Goal boundary.
