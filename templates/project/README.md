# OpenSpec Project Bootstrap

Copy this directory into the root of a participating project. It intentionally
contains project-local artifacts only; do not add product facts or active change
history to the framework repository.

## Contents

- `PRODUCT.md` captures stable product facts and constraints.
- `DESIGN.md` is optional and records enduring system-level decisions.
- `PACKAGE.md` configures project-specific packaging, clean-smoke, content-check,
  release, and rollback evidence.
- `openspec/` is the unmodified OpenSpec `spec-driven` configuration.
- `.opencode/commands/` contains only the five OpenSpec `core` commands
  generated by `@fission-ai/openspec@1.5.0` for OpenCode.

## Prerequisites

The generated command bodies invoke `openspec` directly. Before invoking an
`/opsx-*` command, install the reviewed CLI on `PATH` and confirm its version:

```powershell
npm install --global @fission-ai/openspec@1.5.0
openspec --version
```

`npx --yes @fission-ai/openspec@1.5.0` is suitable for an explicit one-off CLI
operation, but it does not make the bare `openspec` command available to the
generated command bodies. Restart or reload OpenCode after copying the bootstrap
so it discovers the `.opencode/commands/opsx-*.md` files.

Run the preflight from the copied project before using an `/opsx-*` command:

```powershell
PowerShell -ExecutionPolicy Bypass -File .\Test-OpenSpecBootstrapPreflight.ps1
```

It fails when the required CLI is absent or version-mismatched. It reports
unsupported command and skill dependencies from the generated command sources
as actionable warnings; these are OpenSpec `core` profile limitations, not
custom commands added by this bootstrap.

## Start A Change

Use the generated commands in OpenCode:

Use `/opsx-propose <change-name>` to create a change. The OpenSpec CLI's
`instructions` output is authoritative for each artifact's current structure.
The framework's `templates/openspec/` references are not copied with this
bootstrap; use them from the framework checkout only as concise guidance.

For a new project that does not copy this bootstrap, generate the same core
integration with:

```powershell
npx --yes @fission-ai/openspec@1.5.0 init --tools opencode --profile core
```

## Validate

From the participating project root, validate the active change before marking
it verified or archiving it:

```powershell
npx --yes @fission-ai/openspec@1.5.0 validate <change-name> --strict --no-interactive
```

## Core Profile Limitation

The `core` profile generates no custom continuation command for a blocked
change. The bootstrap must not introduce one. Instead, complete the missing
artifact through the installed CLI:

1. Run `openspec status --change <name> --json` and read the `artifacts`
   list. Each `not_done` entry has a stable `id`; do not assume the default
   `proposal`, `specs`, `design`, or `tasks` filenames.
2. For each missing artifact, run
   `openspec instructions <artifact-id> --change <name> --json`. The CLI
   returns the schema-specific frontmatter, required sections, and any
   `contextFiles` paths to populate.
3. Read every `contextFiles` path returned by the instructions.
4. Create or update the artifact at the resolved path so it matches the
   CLI's required structure, then re-run `openspec status --change <name> --json`.
   Repeat until no listed artifact is `not_done`.
5. Re-run `openspec instructions apply --change <name> --json`. The
   `state` should now be `ready` or `in_progress` rather than `blocked`.

This is a documented upstream `core` profile limitation, not a custom
command added by this bootstrap.

On Windows PowerShell, prefer the CLI archive command over the generated
`/opsx-archive` prompt. Its generated POSIX `mkdir -p` step emits a
`ResourceExists` error when OpenSpec's archive directory already exists. The
reviewed CLI supports the platform-neutral alternative:

```powershell
openspec archive <change-name>
```

## Release, Approval, And Pre-Release Validation

Before archive, the generated `/opsx-archive` prompt resolves the `release.md`
and `verification.md` paths from the status JSON, refuses to archive a public
API, schema, data lifecycle, migration, auth, payment, security, or release
boundary change without a recorded release, and re-runs strict OpenSpec
validation when an external action has been recorded. The bootstrap does not
add a custom archive command; it relies on the installed CLI and the
generated prompt's gate so an unapproved release cannot archive.

## Package And Release

Complete `PACKAGE.md` before packaging. Run its selected build/package command,
then verify the resulting artifact in a newly created temporary environment,
record its SHA-256 checksum, and copy evidence into the active change's
`verification.md` and `release.md`.

Packaging is not a release authorization. Before any publish, deploy, tag,
push, merge, or other external write, obtain and record explicit user approval
for the exact version, release notes, target/environment, known warnings,
rollback plan, and external action. After the approved action and post-release
smoke succeed, run strict validation and `openspec archive <change-name>`.
Do not archive a failed, cancelled, or unapproved release.
